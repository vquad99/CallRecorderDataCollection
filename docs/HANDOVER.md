## 2. Hosting (Render, Singapore)

Render account: dubdesk workspace. Blueprint **`ccp-staging`** (manual sync) built from
`render.yaml`.

| Service | Type | What it does |
|---|---|---|
| `ccp-web` | Web service (public) | nginx: serves the app and forwards `/api` to the API. Custom domains attached here. |
| `ccp-api` | Private service | The FastAPI application. Runs `python -m app.cli prepare-deploy` before each deploy (migrations, first Super Admin). |
| `ccp-worker` | Background worker | Celery: turns uploads into delivery files and runs the automatic audio check. Settings copied from `ccp-api`. |
| `ccp-redis` | Key Value (Valkey 8, private) | Work queue and shared sign-in limits. `noeviction`. |
| `ccp-db` | PostgreSQL 16 (private) | All data. |

The same Render account also holds `dubdesk`, `dubdesk-transcriber` and a `dubdesk` database
(Oregon). They are **not** part of this system.

**How code goes live.** Push to `main` → GitHub Actions CI runs every check → Render deploys by
itself (`ccp-web` when `frontend/**` changed, `ccp-api` and `ccp-worker` when `backend/**` changed).
Database migrations run in the pre-deploy step. A change to `render.yaml` itself needs
**Render → Blueprints → ccp-staging → Manual sync**.

**Logs.** Render dashboard → service → Logs. With a Render API key:
`GET https://api.render.com/v1/logs?ownerId=<workspace>&resource=<service id>`.

**One-off commands** (for example creating accounts outside the UI) run as Render one-off jobs on
`ccp-api`: `POST /v1/services/<ccp-api id>/jobs` with a `startCommand`. Render runs the command
without a shell (arguments split on spaces).

## 3. Settings on `ccp-api`

Values marked secret are entered in the Render dashboard (Environment), never in `render.yaml`.
Render asks for `sync: false` values only when a Blueprint is first created and ignores them on
later syncs.

| Key | Value / where it comes from |
|---|---|
| `APP_ENV` | `production` |
| `PUBLIC_APP_URL` | `https://dubdesk.live` (links in emails use it) |
| `DATABASE_URL`, `REDIS_URL` | Linked by Render from `ccp-db` / `ccp-redis` |
| `SECRET_KEY` | Generated by Render |
| `DATA_ENCRYPTION_KEY` (secret) | Fernet key that encrypts participant phone numbers and emails. **Losing it makes them unreadable.** |
| `STORAGE_*` | Wasabi: endpoint `https://s3.ap-southeast-1.wasabisys.com`, bucket `callrec57`, prefix `staging/`, keys (secret) |
| `EMAIL_BACKEND`, `SMTP_*`, `EMAIL_FROM` | `smtp`, `smtp.resend.com`, port 587, user `resend`, password = Resend API key (secret), `Conversation Collection <no-reply@dubdesk.live>` |
| `ADMIN_EMAIL`, `ADMIN_PASSWORD` (secret) | First Super Admin, created once by `prepare-deploy` |
| `ALLOW_DEMO_SEED` | `false` (demo accounts are never created in production) |

The application refuses to start in production without real email, Redis, an https address and
storage keys (`backend/app/core/config.py`).

## 5. Secrets: where they are

Kept on the owner's Mac (`quads`) in `~/.config/ccp/` (folder mode 700, files mode 600). Never in
the repository.

| File | What it is |
|---|---|
| `render_data_encryption_key` | `DATA_ENCRYPTION_KEY` (keep a second copy in a password manager) |
| `wasabi_credentials.csv` | Wasabi access key and secret |
| `resend_api_key` | Resend API key (also the SMTP password) |
| `render_api_key` | Render API key (read logs, run one-off jobs) |
| `test_accounts.txt` | Passwords of the four test accounts |

**Rotate before or at handover**: the Resend, Render and Wasabi keys were shared in chat during
setup. After rotating the Resend key, update `SMTP_PASSWORD` on `ccp-api`; after rotating Wasabi
keys, update `STORAGE_ACCESS_KEY_ID` / `STORAGE_SECRET_ACCESS_KEY`.

**Rotating `DATA_ENCRYPTION_KEY`** (do this at handover, so no earlier holder of the key can read
phone numbers or emails in a database copy): make a new key with
`python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"`, set
`DATA_ENCRYPTION_KEY` on `ccp-api` to `NEW_KEY,OLD_KEY` (new first), let it deploy, run the one-off
job `python -m app.cli rotate-keys`, then set `DATA_ENCRYPTION_KEY` to `NEW_KEY` alone (D-088).

**First admin**: every deploy creates the `ADMIN_EMAIL` account only while no active Super Admin
exists, so renaming or removing that account later is safe. `ADMIN_PASSWORD` can be cleared after
the first deploy.

## 10. Handing the code and system over

1. Transfer the GitHub repository (or add the new owner as admin).
2. Transfer or re-create the Render workspace, the GoDaddy domain, the Resend account and the
   Wasabi bucket; or point them at the new owner's accounts.
3. Rotate every key in section 5 and update the matching Render settings.
4. Hand over `DATA_ENCRYPTION_KEY` securely together with the database.
5. Disable the test accounts.
6. The new team starts from `README.md` (local setup and checks) and this file.
